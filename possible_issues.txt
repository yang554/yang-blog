我会按后端安全、数据库与部署、前端构建、配置和敏感信息几个方面做一次高置信度检查，并区分阻断问题与优化建议。

## 核心结论

项目功能较完整，但目前**不能直接用于公开部署或生产环境**。主要问题集中在鉴权范围、敏感配置、文件上传、密码算法和构建配置。

| 优先级 | 问题 | 风险 |
|---|---|---|
| P0 | API 鉴权规则覆盖不完整 | 未在 Shiro 规则中保护的业务接口可能直接公开 |
| P0 | 存在硬编码密钥和密码 | 数据库、JWT、第三方百度服务凭据可能泄露 |
| P0 | 文件上传接口和路径不安全 | 可能上传恶意文件、覆盖文件或受硬编码路径影响 |
| P1 | 密码使用加盐 MD5 | 高效彩虹表、GPU 破解风险 |
| P1 | CORS 和静态资源配置不安全 | 任意来源可请求接口；静态资源绑定到本机绝对路径 |
| P1 | 刷新令牌、记住登录逻辑未闭环 | 过期后可能误授权或刷新失败 |
| P1 | 缺少测试和完整构建验证 | 多个前端脚本名无效，回归风险高 |
| P2 | 配置和工程结构存在兼容性问题 | 容易出现启动失败、生产部署失败 |

## 详细问题

### 1. 大量业务接口可能绕过 JWT 鉴权

Shiro 中只有以下规则进入 JWT：

- `/api/**`
- `/wx/**`

但绝大多数业务接口使用的是 `/user/**`、`/blog/**`、`/product/**`、`/price/**` 等路径，`ShiroConfig.java` 对它们没有统一保护。

例如：

- `/user/all`
- `/blog/...`
- `/role/...`
- `/TFamilyTreeController/...`
- `/NutritionalRecipe/...`

如果未在控制器中额外检查角色，这些接口可能完全公开。

**整改：**

- 不要依赖路径豁免，采用白名单而不是黑名单。
- 默认要求认证，只有登录、注册、验证码、公开博客接口等明确放行。
- 对管理类接口增加角色或权限校验。
- 增加接口集成测试验证未登录和普通用户不能访问管理接口。

### 2. 密钥和密码已提交到仓库

发现多处真实或示例凭据：

- MySQL 密码和账号：`application.yml`
- RabbitMQ 默认凭据：`application.yml`
- JWT 固定密钥：`application.yml`
- 百度语音 `apikey` 和 `secretkey`：`manifest.json`

**整改：**

- 立即轮换已暴露的密钥和凭据。
- 使用环境变量或私有配置中心。
- 把密钥从 `manifest.json` 和源码移走。
- 后端密钥至少使用 256 位随机值。
- 清理 Git 历史中的敏感提交，不能只删除当前文件。

### 3. 文件上传存在较大风险

`FileController.java` 存在：

- 上传接口对所有人开放。
- 使用文件原始后缀，没有检查 MIME、扩展名或文件内容。
- 文件名可以通过 `/`, `..` 和异常后缀造成路径问题。
- 两套前端和上传目录使用硬编码绝对路径。
- `fileName.substring(...)` 在无后缀文件时可能抛异常。
- 单次文件复制和目录创建逻辑不完整。

**整改：**

- 白名单允许的扩展名和 MIME 类型。
- 限制大小、像素尺寸和文件数量。
- 保存随机文件名，不使用原始文件名。
- 使用 `MultipartFile.transferTo` 和配置化存储目录。
- 敏感图片目录不要映射为可执行静态资源。
- 上传接口要求登录，并按角色限制目录和用途。

### 4. 密码哈希算法过弱

密码使用随机盐加 1024 次 MD5，`SysUserServiceImpl.java`。

MD5 在现代硬件下不适合密码存储，即使使用盐也不够安全。

**整改：**

- 使用 bcrypt、Argon2id 或 PBKDF2。
- Spring Security 或兼容包统一密码编码器。
- 保留旧 MD5 验证逻辑以支持迁移，在用户登录成功后升级为新哈希。

### 5. JWT/记住登录实现不完整

`JwtFilter.java` 中刷新逻辑只有 TODO：

- 过期 Access Token 不会自动刷新。
- 客户端刷新逻辑和服务端实现不一致。
- Remember-me Cookie、Redis 孔令和 JWT 长期有效期叠加，撤销能力较弱。
- JWT 中只有用户名和类型，没有用户状态、角色版本或撤销版本。
- 异常响应会暴露服务端异常信息。

**整改：**

- Access Token 缩短有效期，Refresh Token 单独轮转和撤销。
- 引入 Refresh Token 白名单或版本号。
- 删除已不需要的记住登录自动登录逻辑，或完整实现。
- 禁止在错误响应中暴露异常堆栈或内部消息。

### 6. CORS 配置不一致且过于宽松

`WebConfig.java` 同时使用：

- 固定域名 `allowedOriginPatterns`
- 通配符 `allowedOrigins("*")`

同时未列出所有常用方法。此类配置容易产生跨域规则歧义。

静态资源目录 `WebConfig.java` 固定为 Windows 下的 `D:/MyProject/...`，Linux 或 Docker 部署会失效。

**整改：**

- 使用配置化的允许来源列表。
- 明确允许的 Header 和方法。
- 静态资源目录改为 `file.upload-dir` 配置。
- 容器部署通过 Nginx 或独立对象存储提供静态资源。

### 7. 后端配置存在明显兼容问题

`application.yml` 使用的是：

```yaml
jap:
```

正确配置应为：

```yaml
jpa:
```

因此部分 JPA 配置实际上不会生效。

其他问题：

- `application.yml` 中放置真实可用的数据库和服务地址。
- `pom.xml` 重复配置 Spring Boot Maven Plugin。
- 端口、静态目录、下载地址均写死或依赖特定机器。
- 缓存、事务和定时任务缺少运行环境隔离。

**整改：**

- 修正为 `spring.jpa` 配置。
- 区分 `application-local.yml`、`application-docker.yml` 和生产配置。
- 删除重复 Maven 插件配置。
- 数据库、Redis 和 RabbitMQ 使用环境变量注入。

### 8. RabbitMQ 消费逻辑存在消息可靠性问题

`InteractionEventConsumer.java` 使用：

- Redis 标记幂等。
- Redis 标记有效期只有 1 小时。
- 数据库更新和 Redis 标记不在同一个事务中。
- 失败后重新入队可能无限重试。
- Redis 和数据库操作不会形成强一致性。

**整改：**

- 使用数据库唯一约束记录已处理事件。
- Redis 缓存与数据库操作分离。
- 使用死信队列和有限重试。
- 增加事务或补偿机制。
- 消息消费者校验业务参数。

### 9. 前端构建脚本和依赖存在问题

`blog-front/package.json` 的以下脚本不完整：

```json
"test:unit": "vite test:unit",
"test:e2e": "vite test:e2e",
"lint": "vite lint"
```

这些不是标准 Vite 命令。

同时：

- 没有安装 Vitest、测试库或 Playwright。
- 仓库只有一个后端 Spring Boot 上下文测试。
- `node-sass` 与较新的 Node.js 不兼容风险较高。
- Vue 2/Element UI、Vue 3/Element Plus 的用户体验和技术实现重复维护。
- 管理端存在大量重复页面和兼容文件，例如 `copy.vue`。

**整改：**

- 明确 Vue 2 和 Vue 3 两套前端的定位与维护策略。
- 添加 Vitest、Vue Test Utils 或 Playwright。
- 为关键登录、权限、文件上传和主要 CRUD 写测试。
- 统一锁定 Node.js 版本，并提供 `.nvmrc` 或 Volta 配置。
- 移除未使用的重复依赖和页面。

## 优先整改路线

### 第一阶段：阻断上线问题

1. 修复业务接口 Shiro 鉴权。
2. 轮换数据库、JWT、百度等密钥。
3. 将密码迁移到 bcrypt 或 Argon2。
4. 限制和校验文件上传。
5. 修复或禁用不完整的刷新令牌逻辑。

### 第二阶段：部署可用性

1. 修正 JPA 配置和环境配置。
2. 替换硬编码静态资源、数据库和服务地址。
3. 使用 Docker/环境变量统一部署。
4. 完善 CORS 和静态资源代理。
5. 修正前端构建脚本和 Node 环境。

### 第三阶段：工程质量

1. 添加后端鉴权、核心业务和数据库集成测试。
2. 添加前端关键流程测试。
3. 添加 CI。
4. 引入统一 API 响应、异常处理和参数校验。
5. 分离公开展示端、管理端和移动端的数据权限。
